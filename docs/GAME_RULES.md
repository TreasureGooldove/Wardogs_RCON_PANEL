# 🎛️ 阵营人数与武器 / 装备限制

简体中文 | [English（AI 翻译）](GAME_RULES.en.md) | [返回主页](../README.md)

> 🧪 **试验性功能**：阵营人数控制及武器、装备限制仍在验证中。出现误判、数据异常或执行问题时，请及时停用，并通过 [GitHub Issues](https://github.com/TreasureGooldove/Wardogs_RCON_PANEL/issues) 或 QQ 社区群 1108826972 反馈。反馈请说明面板版本、规则参数、发生时间及已脱敏的处理记录，不要提供密码、Token 或完整私有日志。

侧栏入口：**阵营与装备限制**。两类自动规则均默认关闭，设置保存在面板数据库，不改写 `ServerSettings.ini`。子用户只能查看；主账号启用时必须确认自动操作并再次输入密码。

## 阵营人数控制

若版本窗口显示新版本，但页面仍提示“0 表示不限”、没有“50V50”或“允许加入”，请先 `Ctrl+F5` 强制刷新。仍未恢复时，使用 Release 中的完整 ZIP 更新后端和 `frontend/dist`，重建面板容器，并检查反向代理/CDN 的 HTML 缓存。版本窗口现在同时显示前端构建与后端版本；旧页面提交阵营规则会被拒绝并给出刷新提示。

- Lonestar、Valkyra、Manticore 分别设置人数上限：`0` 表示关闭阵营，`-1` 才表示不限；也可以切换各阵营的“允许加入”。
- **50V50**：选择关闭的阵营并点击“填入 50V50 草稿”，其余两方各 50 人、人数差上限为 1，最低人数门槛为 0。草稿不会自动启用，须保存并按原规则输入主账号密码。
- 可同时开启人数差限制，最大差值为 1–1000（默认 2），只计算开放的阵营，关闭阵营的 0 人不会影响平衡。
- 可设置最低在线人数、超限持续时间（新规则默认 0 秒）和转移间隔（新规则默认 5 秒）；已有保存值保留。
- 每 5 秒检查一次。超过人数上限或最大人数差时，转移到符合上限的较少人数阵营；可选目标人数相同时随机选择。不把未分配阵营或缺失数据当成违规。
- 每次转移一人，优先最近观测到的加入者；同一采样首次出现的玩家按 SteamID 确定顺序，不代表真实加入先后。
- 优先移出关闭阵营的玩家，再减少其他超限数量、改善平衡；不转入关闭或满员阵营。所有开放阵营都满员时显示没有目标阵营，不踢出玩家。
- 未知阵营、缺失可操作 SteamID、服务器未公告换阵营能力或主账号被禁用时，不执行转移。

使用已有采样：页面关注时玩家 / 状态分别约 1 / 2 秒，有人时约 2 / 5 秒，空服约 30 / 30 秒。人数控制启用期间，共享采集器每 5 秒补齐新鲜的玩家和状态样本，不建立第二个独立轮询器；网络失败和限流仍遵循退避。必须启用 `PANEL_HISTORY_ENABLED=true`。最低在线人数为 0 时不设门槛；设为 20 时仍可提前启用，不足 20 人时不做普通平衡，但关闭阵营的玩家仍会按等待与操作间隔移出。

升级会一次性把旧设置中原本表示“不限”的 `0` 迁移为 `-1`，不改变原来的启用状态和正数上限。新版保存的 `0` 在重启后仍表示关闭。旧浏览器页面必须刷新后才能保存；API 写入要求 `limitsVersion: 2` 及请求头 `X-Wardogs-Faction-Limits-Version: 2`，防止旧表单误关阵营。

这属于采样后的纠正，无法在玩家加入阵营之前拒绝加入，也不能保证所有时刻人数都符合限制。自动换边可能影响正在进行的战斗；页面显示的是最近观测人数。

## 物品目录自动同步

目录来自 [WARDOGS 小助手](https://wardogs.t0ki.cn/weapons.html) 的公开数据文件。面板启动后及每 6 小时自动获取，失败后 15 分钟重试；主账号可点击“立即同步物品目录”，最短间隔 60 秒。来源日期、页面日期、最近成功时间、可用数量和同步状态均可查看；数据文件与页面各自标注的日期可能不同，会分别显示。

新增武器与装备自动进入可选目录，**不会自动增加禁用规则或猜测击杀原因**。旧规则及精确 cause 映射保持原样。来源移除的物品保留原 ID 并标记，供已有规则继续识别；不再作为新选择。网络或格式校验失败时保留上次有效目录，缓存保存在面板数据库，首次离线使用随包快照。同步只解析数据，不执行远端 JavaScript；不改变游戏服务器配置。

## 武器强制击杀

1. 配置已有的游戏事件推送（`PANEL_FEED_TOKEN` 与 `PANEL_FEED_ORIGIN`，游戏侧 `[WDServerFeed]`）；可在面板的推送配置入口查看具体内容。
2. 在“武器与装备禁用”中选择物品。
3. 从已接收的实机 `cause` 中选择其击杀原因，或输入精确值。一个原因只能对应一件禁用物品。仅忽略大小写和首尾空格，不做模糊匹配。
4. 主账号确认后启用。收到对应新击杀事件时，面板核对当前观测对局、地图和在线目标，再通过官方 kill 路由强制击杀该玩家。

**检测发生在该武器产生击杀以后。** 官方玩家列表不提供武器、背包、装备清单，不能检测刚拿起武器、未产生击杀的射击、购买或穿戴行为，也不会修改商店或直接删除武器。

选中的物品名称、目录 ID 不一定等于服务器 `cause`；默认映射为空，不自动猜测。规则页面展示最近收到的实际原因，管理员应先确认映射。如果留空，只能通过下面的扩展事件匹配 `itemId`。

默认同一玩家 30 秒内最多尝试击杀一次。只处理新插入事件；重复推送不会再次执行，不补处罚启用前的记录，自杀事件不用于处罚。单批最多处理 10 名玩家，记录接收后超过 10 秒不再操作，数据不完整时跳过。

官方 `eventTime` 是游戏相对时间，不能证明事件在现实时间中足够新。没有 `occurredAt` 的原生击杀事件，只能依据接收时间、当前观测对局和地图检查；延迟事件仍可能影响已复活的玩家。生产端可额外提供带时区的 `occurredAt`，面板会跳过早于启用、过旧或未来时间超出容差的事件。

## 装备检测：事件源扩展

目前官方接口没有穿戴 / 背包清单。**仅在可信事件生产端真实采集并发送以下扩展事件后，才能执行装备限制。** 在 INI 中增加一个设置不会让官方服务器自动产生这种事件；需要服务器插件、事件桥接器或其他受控采集端支持。面板不会从昵称、现金变化或击杀距离推测装备。

沿用 `POST /api/ingest/events` 和独立的游戏推送 Bearer，不能使用机器人 Token：

```json
{
  "serverId": "example-game-instance",
  "events": [{
    "type": "itemUsed",
    "eventId": "example-use-0001",
    "matchId": "example-game-round",
    "mapName": "ExampleMap",
    "steamId": "76561190000000001",
    "itemId": "m4",
    "itemKind": "weapons",
    "occurredAt": "2026-01-01T00:00:00Z"
  }]
}
```

示例为虚构数据，该历史时间不会触发处罚。发送时使用实际发生时间、与原击杀推送一致的实例 / 对局标识，以及规则页面目录中的精确 `itemId`。`itemKind` 为 `weapons` 或 `equipment`，必须与目录匹配；不接受未知 ID。生产端只在真实使用 / 穿戴时报告，不要把物品目录当成玩家持有清单。

`occurredAt` 必须带时区；只处理发生于启用后且距离接收 / 处理不超过 10 秒的事件，未来容差 3 秒。对局关联失败或当前观测陈旧时不处罚。重复 `eventId` 在同实例同事件类型下只消费一次，即便改配置或重启也不重放。

接收响应增加 `itemUsesAccepted`、`itemUsesDuplicates`；原有 `accepted/duplicates` 仍只统计击杀事件，`ignored` 为未知事件类型数量。**事件接收成功不等于已经执行击杀。** 页面“装备扩展事件最近接收”显示是否收到扩展数据；它不证明官方已经支持或每名玩家都被检测。

## 安全边界与记录

### 顶部紧急停止

主账号可在页面顶部点击“停止连接”，输入管理员密码后阻止新的 RCON 请求，并尝试关闭现有连接。采集、自动规则、机器人管理及手动 RCON 操作暂停，不关闭或重启游戏服务器。停止状态保存在面板数据库；重启面板、更改连接设置都不会恢复它。已发送的请求可能已经执行，停止不能撤销；中断且无法确认的写操作仍按不确定结果处理，不自动重试。

点击“恢复连接”同样需要主账号密码。恢复会更换目标版本标识，阵营、物品和反作弊规则需要重新确认启用；服规、暖服等其他已启用功能在获得新采样后按原配置继续运行。本地历史页面仍可查看记录。

接口为 `GET /api/server/connection`（登录用户查看）、`POST /api/server/connection/stop` 与 `POST /api/server/connection/resume`（主账号、同源请求、请求体 `{"password":"管理员密码"}`）。接口不通过机器人 HTTP 网关开放。停止期间上游请求返回 `503 rcon_stopped`；错误密码 `401`，子用户操作 `403`。

### 自动规则

- 每次操作都保留单次尝试回执和面板审计，不重试不确定的写操作。
- 出现超时或审计完成失败时，暂停对应规则；管理员核查后再次确认密码保存才能恢复。
- 面板重启、更换 RCON 目标后，自动规则需要重新保存启用，不沿用旧目标版本。
- 禁用规则不需要输入密码，但仍要求主账号、正常登录和同源请求。
- 游戏服务器需公告 `PATCH /v1/players/{steamId}`（换阵营）和 / 或 `POST /v1/players/{steamId}/kill`（击杀），否则不能启用对应规则。
- 首次上线请保留默认关闭，先检查数据来源与规则映射，再按需由主账号启用。不要在有人的实机上用强制击杀或换边做连通性测试。

面板接口：`GET /api/game-rules` 读取设置、来源状态、物品目录及最近回执；主账号使用 `PUT /api/game-rules/factions`、`PUT /api/game-rules/items` 保存。写入请求包含相应设置及 `targetRevision`；启用还需 `acknowledgeRisk=true`、`password`。这些接口使用面板 Cookie，不通过机器人 HTTP 网关开放。参数错误为 `400 invalid_selection`，目标版本过期为 `409 stale_server_target`，子用户写入为 `403 permission_denied`。

## 随机打乱双方（试验性）

在“50V50 双阵营模式”卡片点击“预览随机打乱双方”。先保存恰好两个开放阵营的规则（可不启用自动控制），上限 `0` 的阵营不会成为目标。面板读取实机名单，随机重分全部在线玩家，在各阵营容量内尽量均分；总容量不足、名单不完整或在线人数不在 2–200 人时拒绝执行。它不按击杀、好友或小队分组，也不改变保存的上限。

预览列出姓名、SteamID、原阵营和目标阵营，60 秒内有效，不发送换阵营命令。主账号再输入密码并确认后才执行。逐人调用官方换阵营接口，不附加击杀、踢出、公告或配置文件写入；期间人数可能短暂超出最终计划，服务器是否接受以回执和复查为准，不保证原生选边限制允许满员互换。

每次操作之间间隔至少 0.5 秒，并释放 RCON 锁；自动人数平衡在打乱执行期间暂停。每次转移前重新读取名单和状态，核对目标版本、规则版本、在线名单与阵营、地图和可用的比赛时间。其他玩家加入、离开、主动换边，或规则变化、返回失败、超时均停止后续操作。缺少比赛时间时，同地图重新开局无法仅靠状态接口可靠识别。顶部“停止连接”会阻止后续请求，已经发送的操作不能撤销。

页面可查看逐人回执，刷新页面后恢复最近任务。完成后核对实机名单；无法核对时显示不确定。操作记录写入面板审计，同一个预览 ID 重复确认不会重发，重启后未完成任务标记为中断，不自动继续或回滚。

接口（仅主账号 Cookie，不开放至机器人网关）：

- `POST /api/game-rules/factions/shuffle/preview`：`{"targetRevision":"当前面板目标版本"}`。
- `POST /api/game-rules/factions/shuffle/{id}/execute`：同一 `targetRevision`，以及 `acknowledgeRisk=true`、`password`。
- `GET /api/game-rules/factions/shuffle/{id}`：查看 `phase`、`plan`、`expires`、`error`；阶段为 `preview/running/completed/stopped/uncertain`。

常见错误：`400 shuffle_two_factions`、`409 shuffle_capacity`、`409 shuffle_stale`、`409 shuffle_busy`。原有权限、密码、同源、紧急停止和能力检查同样适用。请在可控环境验证；不要在有人游玩的服务器上执行测试。

## 官方纯步兵模式

进入 **地图轮换 → 官方纯步兵模式**。页面分别显示实机轮换与当前草稿中带有 `KOTH_InfantryOnly` 的条目数；草稿数量变化不代表游戏已经生效。

1. 点击“全部轮换添加纯步兵”，面板逐图读取当前服务器的地图体验目录（最多 4 个并发读取）。仅对明确支持的地图，在原基础玩法后追加 `KOTH_InfantryOnly`。
2. 查看修改、保持、跳过的条目数量和未处理地图。不支持、目录读取失败/过期、缺少基础玩法的条目不添加，不生成默认玩法、光照或控制区。
3. 检查轮换草稿，点击“应用轮换到服务器”。沿用原有验证、配置版本检查和账号密码二次验证，确认后才提交。
4. 游戏重建轮换，从下次正常切图开始使用。生成草稿不会结束比赛或重启服务器；无需为了启用而立即切图。若服务器未采用新轮换，请先核对实机返回，不自动重启。

“全部轮换移除纯步兵”仅移除这个修饰项，保留基础玩法、其他修饰项、重复条目、排序、光照、控制区及原文的其他字段、注释与换行。若它是唯一体验则跳过；重复体验字段或无法安全解析的原文会拒绝修改。开关不改变轮换本身的启用状态。可在“模式／修饰符”中为新条目单独选择原玩法和纯步兵。

以 Bakurani 为例，体验组合为 `Bakurani_KOTH_02+KOTH_InfantryOnly`；实际基础玩法必须取自本次实机目录和原轮换，不应直接套用示例覆盖整份配置。该功能使用游戏原生规则，其具体武器与载具限制由游戏版本决定。

只读用户可查看实机轮换统计；修改沿用已有“配置”权限。所有写入仍走仅允许改变轮换段落的 `/api/server/config/rotation` 接口，不新增自动处罚、击杀或任意命令入口。启用与停用都需要在应用草稿时输入账号密码。
